MEANINGFUL PROGRESS — DEPLOYED SECURITY REMAINS CONDITIONAL

The new Lean proofs make the attack cases explicit without pretending the open work is finished.

Three new modules make the security claim more precise. Within explicitly defined Lean models, they reduce false acceptance and one fixed-victim attack event to named failures. They do not yet prove that the models cover every deployed Tag-67 attack or that each failure is negligibly likely.

What the three modules prove

ModuleWhat Lean now provesWhat it does not prove
ApplicationMerkleBinding.lean If two different note leaves are opened at the same depth-20 tree position and reach the same root, the paths reveal two different ordered node inputs with the same Poseidon2-M31 node-hash output. It also proves that changing the direction bits can simply select a different real position, so that case must not be called a collision. It gives no numerical collision bound for the custom node hash and does not concern the separate SHA-256 trees inside the proof system.
V5DeployedFalseAcceptance.lean It takes three caller-supplied definitions of failure and proves their union bound. If callers prove that they are the actual deployed selector failures and supply accepted-run extraction, Poseidon2 faithfulness, the existing width, round, transcript, commitment, Fiat–Shamir, and per-branch premises, Lean derives the corrected work-normalized 2^-100 bound. It also states the ordinary probability as at most min(1, T / 2^100), where T is the random-oracle query budget and 1 <= T <= 2^128. It does not prove that those definitions correspond to selector values 0, 1, and 2, or prove any of the other inputs for the deployed Rust program.
V5FixedVictimTheftGame.lean It fixes one victim note and defines an attack event. Lean proves that this event falls into one of five mathematical cases: extraction failure, recovery of the victim credential, a nullifier collision, a second opening of the victim note, or a different leaf at the same tree position. A conditional chain-facing theorem adds a PDA alias, a runtime or state failure, and an invalid victim setup, then proves the corresponding eight-term probability sum. It does not supply probabilities for those eight cases and does not itself connect an arbitrary deployed Tag-67 transaction to the mathematical attack model.

What remains unproved

The largest open item is still the connection from deployed acceptance to a valid witness:

  • Show that every arbitrary proof accepted by the exact Tag-67 parser and verifier yields the authenticated rows needed by the full private-spend relation. This includes polynomial commitments, FRI, Fiat–Shamir, proof-tree authentication, byte decoding, public-input binding, and live account state.
  • Identify the three caller-supplied failure definitions with the actual selector-0, selector-1, and selector-2 failures, and prove that the cited coding and proof-system results apply to those schedules, including the separate proof-of-work hashes and the exact Rust challenge order.
  • Supply real security bounds for the custom Poseidon2-M31 owner, note, nullifier, and tree-node functions. Test vectors check selected outputs; they do not prove one-wayness or collision resistance.
  • Connect the fixed-victim model to the exact deployed code and Solana's account locking, rollback, ownership, and marker persistence. The game must also rule out duplicate victim credentials at setup.
  • Handle attackers that have already observed other honest proofs. The extractor needs the adversarial prover and its random-oracle transcript; public proof bytes alone are not enough.
How serious is this? It is a high-priority gap in a claim about security against malicious proof makers. No concrete forgery or mathematical break was found, and the archived demonstration remains strong evidence for that one honest execution. The repository should not yet claim a proved deployed 100-bit false-acceptance rate or a numerical theft-resistance bound.

The bump-255 correction

The nullifier marker used by the finalized mainnet transaction had bump 255. However, deployed source commit 06788d44 called verify_and_apply_atomic_payment_state, which derived the PDA but did not require the derived bump to equal 255. The required-bump wrapper was added later.

Therefore bump 255 is an observed fact about the landed marker, not an enforced rule of the deployed verifier. Repeat protection for the same nullifier still follows from deterministic PDA derivation and the stored marker, subject to Solana runtime behavior. A different nullifier resolving to the same PDA is kept as a separate failure case in the new theft model.

Safe publication wording

It is accurate to say that Lean checks the Merkle collision reduction, a complete case split for the fixed-victim attack event defined in the Lean model, and a conditional false-acceptance bound over three caller-supplied failure events. It is not accurate yet to say that deployed V5 theft resistance or the deployed 100-bit security claim has been fully proved.
