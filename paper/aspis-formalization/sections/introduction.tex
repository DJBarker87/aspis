\section{Introduction}
\label{sec:introduction}

Succinct transparent arguments reduce a statement about a computation to a
small number of algebraic and authenticated-opening checks.  A deployed
private-spend verifier adds another set of obligations.  The proof must bind
the exact public statement, the verifier must authenticate every value it
uses, the nullifier must control a real state transition, and the
implementation must preserve the order assumed by the Fiat--Shamir argument.
Each part is simple to describe in isolation.  Their composition is not.

\Aspis{} brings that composition into one auditable development.  It has three
different kinds of evidence:
\begin{enumerate}[leftmargin=*]
  \item Lean definitions and proofs for the mathematical model;
  \item focused Rust-to-Lean translations and source-shaped bridge theorems;
  \item build and transaction records for the binary that ran on Solana.
\end{enumerate}
Together they describe the mathematical verifier, selected production code,
the compiled program, and one finalized execution.  The report keeps the
scope of each result clear so that future source proofs can be added without
changing the mathematical statement.

The mathematical background is kept short.  Most of the report is devoted to
the formal model, security experiment, proof reductions, and source locations.
Lean declarations are cited by stable names instead of line numbers, which
change during maintenance.

\subsection{Contributions}

The main checked results reported here are:
\begin{itemize}[leftmargin=*]
  \item a deterministic proof that extracted arithmetic, hash, and Merkle
        rows imply the complete one-input/one-output spend relation;
  \item exact finite-field and circle-domain facts, including the deployed
        M31 circle generator order and distinct released evaluation points;
  \item exact identities for the initial circle encoder and the four later
        encoders, with the later polynomial-code distances checked in Lean;
  \item a causal four-round candidate argument that follows one initial
        decoder candidate through every fold;
  \item the exact probability for eighteen distinct queries drawn by the
        bounded first-occurrence sampler, and the corresponding fixed-set
        miss calculation;
  \item a byte-level transcript schedule recording absorbs, squeezes, work
        checks, roots, salts, messages, nonces, and the query selector;
  \item a five-tree Merkle model covering value/salt records, binary and
        radix-four hashing, shifted indices, path orientation, exact section
        order, and rejection of unused path bytes;
  \item one work-normalized probability experiment with nineteen disjointly
        listed failure kinds and a checked 70/30 split for a conditional
        \(2^{-100}\) endpoint;
  \item fixed-victim and adaptive attack reductions that state each remaining
        cryptographic, extraction, source, and runtime failure separately;
  \item explicit models of the spent-marker write, account checks, rollback,
        close/refund behavior, and the required marker-address bump.
\end{itemize}

The formal source at the paper snapshot contains 221 maintained Lean modules,
102,832 lines, and 3,269 declarations introduced with \code{theorem}.  These
counts describe the repository; they are not a measure of security.  The
principal results used in this paper include \texttt{\#print axioms} checks.  At
the selected entry points, Lean reports only \code{propext},
\code{Classical.choice}, and \code{Quot.sound}, which are standard Lean and
mathlib foundations~\cite{deMouraUllrich2021Lean4,MathlibCommunity2020}.

\subsection{Scope}

The \(2^{-100}\) result is stated for the work-normalized experiment defined in
Lean.  The main project-specific work still open is the universal equality
between an accepting production verifier run and the complete Lean trace,
together with the final V5-specific FRI/Fiat--Shamir event connection.
Published decoding results, SHA-256 and Poseidon2 security, the proof
assistant, compiler, and Solana runtime are stated as ordinary trusted inputs.
The mathematical privacy and theft reductions are reported separately from a
full production privacy or raw theft bound.  \Cref{sec:limitations} gives the
complete list.

\subsection{Reading guide}

\Cref{sec:background} describes the spend statement and fixed proof profile.
\Cref{sec:lean-model} presents the Lean model and its main definitions.
\Cref{sec:implementation} explains what is and is not connected to production
Rust.  \Cref{sec:soundness} gives the single probability experiment and final
conditional bound.  \Cref{sec:theft-state,sec:privacy} cover theft resistance,
state behavior, and privacy.  \Cref{sec:proof-design} records proof choices
that prevent several attractive but invalid shortcuts.  The evaluation
follows.  The appendices collect assumptions, a dependency map, theorem index,
failure ledger, and source-audit checklist.
