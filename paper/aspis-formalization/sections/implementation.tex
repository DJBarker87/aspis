\section{Connection to the implementation}
\label{sec:implementation}

\subsection{Production verifier path}

The deployed verifier reads a fixed proof body, reconstructs the public
statement digest, replays the transcript, verifies the six work records,
derives the selected eighteen queries, authenticates five opening sections,
checks the four FRI folds and final polynomial, checks the relation, and only
then calls the atomic state transition.

The main production functions discussed in this report are:
\begin{itemize}[leftmargin=*]
  \item transcript state and SHA-256 framing in
        \code{crates/aspis-core/src/transcript.rs};
  \item transcript replay, work checks, relation calls, and verifier control
        flow in \code{programs/aspis-verifier/src/v5_cu_probe.rs};
  \item preparation and consumption of FRI values in
        \code{programs/aspis-verifier/src/v5_fri_checks.rs};
  \item the five-section opening driver
        \code{verify_v5_private_openings_from_proof};
  \item the focused opening helper
        \code{verify_state_only_private_opening_from_proof_with_topology};
  \item account validation, marker creation, and pool mutation in
        \code{verify_and_apply_atomic_payment_state_traced_inner};
  \item proof-account refund in
        \code{refund_program_owned_proof_account}.
\end{itemize}

The production Rust is larger than this list.  The list identifies the path
for which this paper gives formal anchors.  Dispatch, upload, unrelated
diagnostic modes, host retry code, compiler lowering, and runtime execution
are not silently included.

\subsection{Focused extraction}

Charon translates selected safe Rust into its LLBC representation.  Aeneas
then produces pure Lean functions and proof obligations.  Broad Solana
functions contain framework types, function pointers, syscalls, and control
flow outside the selected proof scope, so the project uses focused
extractions for the verifier callback and source-shaped models for the
surrounding transaction and runtime behavior.

For each connection we distinguish three statements:
\begin{enumerate}[leftmargin=*]
  \item a pure Lean model has the desired property;
  \item the source-shaped composition equals that model;
  \item the production Rust function equals the source-shaped composition.
\end{enumerate}
Only the third statement turns the first two into a production theorem.  For
the selected accepted callback, the source proof now reaches the complete
relation caller.  It derives the main accumulator's twelve terminal weights,
the compact accumulator's complete state evolution, and both final dot
products from the same accepted four-round execution.  The theorem still
takes the opaque terminal evaluator as a named interface; boundaries outside
the selected source path remain named as well.

\subsection{Transcript coverage}

The pure transcript result is detailed.  It records every label and payload,
expands each typed event to primitive hash inputs, places each work check
immediately before its nonce absorb, and proves that the values supplied to
the FRI and relation code come from the named squeeze results.  The source
adapter also decodes the exact fixed-body slices and exact selector byte.

Focused translations cover the production field, nonzero-field,
out-of-domain, secure-circle, and distinct-query samplers.  The accepted-entry
proof connects their outputs to the exact values consumed by the FRI and
relation calls in the same successful execution.  The generic equality
\code{ExactRustV5TranscriptDriverEquality} remains an interface for other
callers, but it is not a premise of the completed accepted-entry sampler
proofs.

The transcript hash itself is separated from hash security.  The deterministic
model says which bytes are hashed and in which order.  The cryptographic model
defines implementation-divergence, collision, preimage, transcript-divergence,
and random-oracle events.  Known-answer tests can support the implementation
equality on selected inputs, but they cannot prove collision resistance or
random-oracle behavior.

\subsection{Merkle coverage}

The opening proof follows the actual helper and five-section driver reached by
the accepted production entry.  It inverts the successful generated execution
into five exact section traces.  Each trace records the encoded value and salt,
the tree position, the radix-four levels, the binary cap, the frontier, and the
literal returned remainder.  The driver proof fixes the five tree order and
shows that the last call leaves no trailing opening bytes.

Those traces construct an \code{AcceptedV5Forest}.  A separate consumer proof
shows that the later FRI checks read the value portions returned by these same
opening calls.  Outside the explicit SHA-256 collision event, the values are
unique under the supplied roots and query set.

Thus the accepted-path Merkle theorem does not assume that Rust acceptance
yields an authenticated forest.  It derives the forest and the consumer
observation from the successful translated execution.  SHA-256 collision
resistance and the Solana SHA syscall semantics remain separate assumptions
after this deterministic source connection.

\subsection{Relation and candidate coverage}

The relation source model covers the prepared point claims, four unrolled
round calls, staged claim updates, fold challenges, and final coefficients.
Theorems in \code{V5RelationStressSourceBridge} show that the source-shaped
caller implies the pure modeled relation checks and that its final
coefficients equal the values supplied to FRI.

The accepted-entry caller is connected to the unchanged extracted relation
verifier through the exact 76 decoded claims, four prepared claims, initial
relation value, and 58-field tail consumed by the four ordered rounds.  The
same four fold challenges and final polynomial are shared with the FRI call.
For the general accumulator,
\code{releasedTerminalDotCandidateExact} proves the complete extracted
twelve-component dot product, including the dense and deferred grouped loops.
The accepted-run proof identifies each terminal component with its maintained
weight and identifies the resulting dot with the verifier's returned value.
For the compact accumulator, the constructor, four fold cases, final assembly,
and four-term dot product are connected through the corrected extracted
iterator.  \code{accepted_composite_security_conclusion} uses both results in
the theorem that starts from one successful selected translated verifier call.

The first handwritten Lean replacement for the compact outer fold rebuilt the
array from an empty terminal iterator and therefore discarded its writes.  A
Lean counterexample records that error, and the proof now uses a corrected
wrapper that rebuilds from the updated original iterator.  This was an error in
the proof artifact, not in the Rust function or deployed program.  An extended,
pinned Aeneas translation of the unchanged function now emits the correct
mutable-iterator handback and compiles under Lean 4.32.  The accepted-run
theorem connects that generated caller to the fold-semantics proof.

The final candidate construction also has to connect authenticated values and
transcript challenges to the eligibility, support, message, and response
functions used by the correlated-agreement theorem.  The mathematical theorem
is universal over data satisfying that interface.  The production mapping to
that interface is still an external source obligation.

\subsection{State-transition coverage}

The state bridge gives a source-shaped description of the current spend and
close functions.  It proves exact account counts, refund-account selection,
the bump-255 check, successful state writes, rejection of an existing marker,
and agreement between current and recorded behavior at the observed bump.

The predicates \code{ExactCurrentRustStateEquality} and
\code{ExactRustCloseEquality} identify the remaining Rust-to-model statements.
The structure \code{ProductionRuntimePremises} then names account locking,
system-program behavior, rollback, and finalized persistence.  The theorem
\code{runtime_premises_hold_outside_iff_no_named_failure} makes their failure
events explicit.  The model proves what follows if the runtime premises hold;
it does not formalize the entire Solana runtime.

\subsection{Source, binary, and chain identity}

The deployed binary is identified by SHA-256 and size.  A clean build from the
recorded source and pinned tools reproduced the binary byte for byte.  The
release record then identifies the deployed program and finalized transaction.
This establishes a useful chain of evidence:
\begin{equation}
  \text{recorded source} \longrightarrow
  \text{recorded binary} \longrightarrow
  \text{recorded transaction}.
\end{equation}
The first arrow depends on the build tools and the reproducibility record.
The second depends on the loader and chain records.  Neither arrow proves the
cryptographic soundness of all accepted inputs.

The formal paper snapshot is
\code{45d0ec466133bba6b7c52a39a288809a4943abf2}~\cite{AspisRepository2026}.
The clean source commit used
for the deployed binary is
\code{06788d44d30ea8cbd391899dddaf6f0acc6e4a3f}.  They are intentionally
reported as different objects: the formal development continued after the
deployment.
