\section{Machine-checked development}
\label{sec:formalization}

The repository includes a Lean~4 formalisation
\cite{deMouraUllrich2021Lean4} of finite algebra and theorem composition used
by the project.  The \path{AspisFormal/} project kernel-checks 30-bit
no-wrap/value arithmetic, range, balance and asset clauses, the finite
q18/g37 probability ledger, circle-generator order and fibre distinctness,
QM31 tower facts, distribution-level masking lemmas, and pinned Poseidon2
known-answer executions.  Its maintained audited theorems use only
\texttt{propext}, \texttt{Classical.choice}, and \texttt{Quot.sound}; the
project contains no \texttt{sorry} or custom axiom.

That statement must not be enlarged into a proof of complete deployed
acceptance.  The new \texttt{V5AcceptedSpendRelation} theorem proves that a
normalized package containing zero arithmetic residuals, typed Poseidon2
inputs, the eleven checked two-round transitions of each permutation, both
Merkle paths with shared bits and siblings, and the exact six public-field
matches implies the full spend relation, relative to
\texttt{Poseidon2Faithful}.  The package is not raw proof bytes.  No current
theorem derives all of those facts from arbitrary accepted V5 execution.  The
published Johnson/MCA/PCS, Fiat--Shamir, extraction, and anti-malleability
results likewise enter as assumptions.
Hash security and random-oracle modelling remain cryptographic assumptions.
The proof-status table in \path{AspisFormal/README.md} distinguishes these
assumptions from conclusions Lean actually checks.

After the q18/g37 mainnet execution, the project used Charon and Aeneas to
compare selected V5 Rust functions with Lean models
\cite{HoProtzenko2022Aeneas}:
\[
  \text{selected production Rust}
  \longrightarrow
  \text{Aeneas-generated Lean}
  \longrightarrow
  \text{maintained component model}.
\]
The final Lean theorem collects a source-extracted Component-A result at the
selected schedule, a Component-B result, Component-C fold and public-output
results, and the Tag-67 work-wire/six-step verifier.  This is not a theorem of the form
``arbitrary production-verifier acceptance implies the complete spend
relation.''  The Component-B proof assumes that the relevant Rust calls
succeeded and that inputs have the required lengths and field encodings.  The
Component-C proof assumes that its folded Rust values, coefficients, and
challenges equal the Lean values.  No theorem currently proves that every
accepted production proof meets all of those assumptions in one real run.

The Tag-67 work-checking theorem retains one concrete assumption: the stored
grinding-digest call must equal the hash used in Lean on
\(\texttt{DOM\_GRIND}\mathbin\Vert\texttt{nonce\_le64}\).  Given that
equation and successful generated wire guards and reads, projection, the
leading-zero predicate, and the ordered six work checks are theorem
conclusions.  This is the only extra equality in the Tag-67 theorem; it is not
the only assumption in the full Rust-to-Lean argument.

The V5 repair proves that the legacy degree-28/full-field batch expression is
a strict conservative upper bound for the deployed degree-18/nonzero-field
term; it never equates them.  It also separates the old 31-item serialized
trace into the initial committed data \(m_0\) plus exactly 30 challenge
rounds.  Thus a cap of 32 remains numerically conservative, but is not the
exact V5 round count.  The fractional 100.161-bit result belongs only to the
q18/g37 case study.

The final V5 calculation assumes that the listed failure cases cover every
false proof; the opened values belong to the claimed code; the cited coding
and Fiat--Shamir papers apply to this exact mixed M31/QM31 protocol; each
separately hashed proof-of-work value justifies the work factor used for its
later challenge; Rust samples challenges and orders transcript messages as
Lean says; the commitments have the assumed security; and the three branches
and six work checks are counted once each.  Lean proves the numerical result
if these statements are true.  It does not prove the statements themselves.
Consequently V5 is not presently an end-to-end proved 100-bit system.

The same problem applies to privacy and authorization.  Lean proves useful
masking facts for individual parts, but there is no theorem connecting the
complete deployed V5 prover, its randomness, transcript, commitments,
serialization, and published proof into one zero-knowledge result.  The
repaired authorization theorem no longer assumes that the compressing
nullifier hash is globally one-to-one.  It is instantiated with the exact V5
spend relation and proves that an accepted prover execution whose extracted
secret is wrong implies extractor failure or a different input with the fixed
target nullifier.  A second theorem handles a different valid opening of the
exact same fixed input leaf by reducing it to extractor failure or a second
preimage of the combined owner-and-note commitment.  These are valid logical
reductions, not a complete efficient-adversary theft game.  Deployed extraction,
target sampling or uniform fixed-target assumptions, commitment bounds, the
alternative-leaf Merkle reduction, and the full code connection remain
external, so no numerical V5 theft-resistance bound is claimed.
